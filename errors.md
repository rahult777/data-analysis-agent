**2026-04-28 | anthropic==0.25.0 TypeError: Client.__init__() got an unexpected keyword argument 'proxies'**
Root cause: anthropic==0.25.0 requires httpx<0.25.0 but supabase==2.28.3 requires httpx>=0.26, causing a version conflict. The proxies argument was removed in newer httpx versions.
Solution: upgraded anthropic from 0.25.0 to 0.97.0 which supports httpx>=0.25.0, compatible with supabase's requirements. Updated requirements.txt accordingly.

**2026-05-06 | FutureWarning: sns.boxplot with all-NaN column and pandas 2.2**
Root cause: seaborn internals emit a FutureWarning when sns.boxplot receives a column that is entirely NaN values, triggered by pandas 2.2 internal behavior change. The except block in generate_boxplot catches this safely and returns None without crashing.
Solution: already handled gracefully by the try/except pattern in viz_tools.py. No code change needed. Be aware this warning may appear in logs when datasets have all-NaN numeric columns after cleaning.

**2026-05-07 | PauseResumeRequest fields corrupted by Code Review plugin**
Root cause: Code Review plugin changed response: dict to action: str and user_input: Optional[str] without being instructed to. The resume endpoint expects a dict containing the full user decision to write to user_pause_response in the database.
Solution: follow-up fix commit (9388400) restored PauseResumeRequest to exactly one field: response (dict). Verification: python -c 'from backend.models.schemas import PauseResumeRequest; print(PauseResumeRequest.model_fields)' must print only response field.

**2026-05-15 | test_analyzer.py sepal_width and petal_width excluded from numeric_cols on iris.csv**
Root cause: classify_columns excludes any column whose name contains "id" as a substring — "width" contains "id" so sepal_width and petal_width are excluded from numeric_cols on iris.csv. This is documented behavior not a bug in the code.
Solution: test_classify_columns_numeric updated to assert sepal_length and petal_length are present and sepal_width and petal_width are absent, with an explanatory comment. Any future fixture or test involving columns with "id" anywhere in the name must account for this exclusion.

**2026-05-17 | Build error: `border-border` class does not exist in globals.css:3:1**
Root cause: globals.css contained `@apply border-border outline-ring/50` in the universal `*` selector. `border-border` is a shadcn/ui shorthand that requires Tailwind v4. The project uses Tailwind v3 (tailwind.config.ts present), where this utility does not exist as an @apply-able class. This was a pre-existing issue in the frontend scaffold that was exposed on first compile.
Solution: Replaced `@apply border-border outline-ring/50` with the Tailwind v3 equivalent using explicit CSS custom property reference.

**2026-06-03 | Pipeline SYSTEM_ERROR "Failed to parse model response as JSON: Unterminated string starting at line 354 column 24 (char 29287)" — Analyzer LLM output truncated at max_tokens**
Context: First true end-to-end pipeline run on real LLM calls (prior runs were unit tests with mocked responses). Triggered during the Results-page Phase 1 verification gate, uploading tests/fixtures/iris.csv. Pipeline reached Profiler (ok) -> Cleaner (ok) -> Analyzer (FAILED); Explainer never ran.

So the LLM spends thousands of output tokens regenerating data that is immediately discarded. On iris.csv (only 15 rows; small-n made the model verbosely hedge every field with "n=15, well below the 50-row floor") the response exceeded 8000 tokens and was cut off mid-string. parse_json_response (backend/agents/profiler.py:124) then failed json.loads and re-raised as SYSTEM_ERROR. No stop_reason=="max_tokens" check existed, so truncation surfaced as a cryptic JSON parse error instead of a clear "response truncated" message. (Charts WERE generated successfully before the failure — 10 PNGs + 1 scatter HTML on disk — but chart_paths/analysis_report were never saved to the DB because the Analyzer errored before its save step, and executive_summary/insight_report were never produced.)
Solution (applied, NOT yet validated end-to-end): In analyzer.py, added module constant ANALYZER_MAX_TOKENS = 32000, used it in the messages.create call (was max_tokens=8000), and added a guard that raises a clear ValueError when response.stop_reason == "max_tokens". Module verified to import cleanly. The re-run that would validate this was deferred (session ended before re-running). Anthropic SDK non-streaming default timeout is 10 min (verified via Context7); 32000 is only a ceiling, not forced output, so it won't approach the timeout for iris.
Pending follow-ups: (1) APPROVED BUT NOT YET APPLIED — the Explainer (backend/agents/explainer.py:127) has the identical max_tokens=8000 and a large 3-layer output (5 executive bullets + analyst narrative + technical methodology/code blocks); apply the same fix (raise to 32000 + stop_reason guard) BEFORE the next gate run to avoid a second truncation failure. Its smaller custom-question calls (max_tokens=2000/1000) are not in the gate path. (2) Deeper fix (real root inefficiency, out of scope so far): stop instructing the Analyzer to echo the computed stats blocks in its JSON since Python overwrites them — would shrink analyzer output substantially. (3) Profiler and Cleaner completed fine at max_tokens=8000 in this run. (4) Unrelated observation: tests/fixtures/iris.csv is a 15-row stub, not the 150-row dataset described in docs/infrastructure.md:282 — docs are inaccurate; tests are self-consistent (assert row_count == len(iris_df)).

**2026-06-04 | Pipeline SYSTEM_ERROR "Streaming is required for operations that may take longer than 10 minutes" — main synthesis call rejected client-side at max_tokens=32000**
Context: Phase 1 gate re-run after applying the 2026-06-03 fix (ANALYZER/EXPLAINER_MAX_TOKENS=32000 + stop_reason guard). Uploaded tests/fixtures/iris.csv. Pipeline reached Profiler (ok) -> Cleaner (ok) -> Analyzer FAILED at backend/agents/analyzer.py:687 (the main messages.create call). Explainer never ran but carried the identical latent defect.
Root cause: The Anthropic SDK computes the non-streaming request timeout from the max_tokens CEILING, not actual output. In anthropic/_base_client.py:_calculate_nonstreaming_timeout: expected_time = 3600 * max_tokens / 128000; if expected_time > 600s (i.e. max_tokens > ~21,333) it raises ValueError("Streaming is required...") BEFORE any HTTP request. 8000 -> 225s (why Profiler/Cleaner and the old code passed); 32000 -> 900s (rejected). The 2026-06-03 note claimed "32000 is only a ceiling, not forced output, so it won't approach the timeout" — that reasoning was WRONG: the SDK caps on the ceiling regardless of real output. The rejection is client-side, so the Analyzer call cost $0 (never reached Anthropic); only Profiler+Cleaner billed, making this failed run cheaper than the prior $0.74 run.
Solution (applied; imports + unit tests clean; end-to-end gate validation pending): Switched BOTH main synthesis calls to streaming — backend/agents/analyzer.py:~687 and backend/agents/explainer.py:~133 now use `with client.messages.stream(...) as stream: return stream.get_final_message()` (wrapped in asyncio.to_thread). messages.stream() lifts the non-streaming 10-min guard (per the Anthropic SDK long-requests guidance / claude-api skill streaming doc). get_final_message() returns the same Message object messages.create() did, so the existing stop_reason=="max_tokens" guard and parse_json_response(response.content[0].text) are unchanged. max_tokens stays 32000 (under Sonnet 4.6's 64K streaming output cap); model unchanged (claude-sonnet-4-6). The smaller custom-question calls in explainer.py (max_tokens=2000/1000) remain non-streaming (well under the ~21.3K threshold). Verified: both modules import cleanly; 40 unit tests pass / 5 integration tests skipped. NOT yet validated end-to-end — the next gate re-run will confirm the full Profiler->Cleaner->Analyzer->Explainer path on real LLM calls.
