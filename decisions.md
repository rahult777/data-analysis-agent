## Project Foundation Decisions

**2026-04-13 | File size limit set to 100MB, not 50MB**
The original CLAUDE.md specified 50MB. Changed to 100MB after reasoning that a CSV with 500,000–1,000,000 rows — a genuinely large real business dataset — typically falls in the 80–150MB range. 50MB was too restrictive for real-world business use. The system's RAM usage at 100MB is well within acceptable bounds for any reasonable server.
Alternatives considered: 50MB (original), 200MB (too permissive for a first version), unlimited (no protection against accidental large uploads).

langgraph==0.1.0 does not exist as a published version — pip confirmed this with an error listing available versions which skip from 0.0.x directly to 0.1.1. The closest correct version was 0.2.0.
Alternatives considered: 0.1.1 (too old), 0.2.0 (chosen — stable and compatible).

langsmith==0.1.63 caused an irresolvable dependency conflict with langgraph==0.2.0, which requires langsmith>=0.1.112. Pip entered infinite backtracking trying to satisfy both simultaneously. Updated to 0.1.147 which is compatible with langgraph==0.2.0 and all other packages.

**2026-04-13 | supabase version changed from 2.4.0 to 2.28.3**
supabase==2.4.0 had internal dependency conflicts — its sub-packages (gotrue, storage3, supafunc) disagreed on which version of httpx they needed. These conflicts could not be resolved without upgrading supabase itself. 2.28.3 is a self-consistent version where all sub-packages agree on httpx>=0.26,<0.29.

**2026-04-13 | pip install uses --use-deprecated=legacy-resolver flag during setup**
The new pip dependency resolver entered infinite backtracking due to version conflicts between langsmith, supabase, and their transitive dependencies. The legacy resolver installs packages without this backtracking behavior. The actual packages installed are identical — only the resolution algorithm differs. This flag is a one-time setup decision and does not affect runtime behavior.
Alternatives considered: New resolver (causes infinite backtracking), legacy resolver (chosen — identical packages, no backtracking).

**2026-04-13 | Supabase tables created with session_id column for minimal authentication**
Without any authentication, any user who knows an analysis_id could access another user's analysis results. Adding a session_id UUID that is generated on upload and required on all subsequent requests provides a simple, effective first layer of protection without implementing full auth. Full Row Level Security (RLS) will be added before production deployment.
Alternatives considered: No auth (insecure), full JWT auth (too complex for current stage), session_id (chosen — simple, effective, easy to upgrade later).

**2026-04-14 | Cleaned dataset persisted to Supabase Storage as parquet, not kept in local memory**
The Analyzer and Explainer both need the cleaned dataset. If it lives only in memory, the pipeline cannot be resumed after a crash. If it lives only in local storage, it cannot be accessed by serverless functions or multiple worker processes. Parquet is compact, fast to read, and preserves dtypes exactly — a cleaned DataFrame round-trips through parquet without any data loss. Supabase Storage provides persistent, accessible cloud storage without requiring a separate service.
Alternatives considered: In-memory only (not resumable), local filesystem only (not scalable), Supabase Storage as parquet (chosen — persistent, accessible, dtype-preserving).

**2026-04-14 | pgvector and vector search explicitly removed from the system**
This system does not perform semantic search over analyses or questions. Every query is either a direct database lookup (get analysis by ID) or a pandas computation on a specific dataset. Adding vector search would add complexity, cost, and latency with zero benefit for the current use cases.
Alternatives considered: Add pgvector for semantic question matching (over-engineered for current needs), no vector search (chosen — YAGNI, keep it simple).

**2026-04-14 | Domain confidence pause threshold set at 80%**
Below 80% confidence, the Profiler's domain hypothesis is not reliable enough to drive domain-specific cleaning and analysis decisions downstream. At 80% or above, the hypothesis is reliable enough to proceed without interrupting the user. 80% was chosen as the threshold after reasoning that a world-class analyst would seek confirmation when they were less than 80% certain about the domain.
Alternatives considered: 70% (too permissive — allows too much uncertainty), 90% (too strict — would pause too often on clear cases), 80% (chosen — good balance between confidence and flow).

**2026-04-14 | Missing value pause threshold set at 30%**
A column with over 30% missing values is a significant data quality issue that changes the meaning and reliability of any analysis involving that column. Below 30%, imputation is a reasonable automated decision. Above 30%, the decision about whether to impute, exclude the column, or exclude the rows has material impact on the analysis — the user must be informed and must choose.
Alternatives considered: 20% (too sensitive — would pause too often on slightly messy data), 50% (too permissive — allows major quality issues to proceed silently), 30% (chosen).

**2026-04-14 | Three user types with three simultaneous output layers**
A business owner, a data analyst, and a data scientist all need the same underlying analysis but translated differently. Producing only one output layer means some users get too much jargon or too little depth. Producing separate analyses for each type is too slow. The solution is one analysis, three translation layers produced simultaneously by the Explainer. Users optionally self-identify to prioritize emphasis, but all three layers are always present.
Alternatives considered: Single output for all users (wrong depth for most), separate analyses per type (too slow), three simultaneous layers (chosen).

**2026-04-14 | Analyzer self-evaluation checklist has exactly 5 criteria**
The 5 criteria were chosen to cover the complete analytical surface: concerns flagged by the Profiler (a), strong correlations (b), anomaly explanations (c), chart completeness (d), and identification of the most important finding (e). Together these 5 criteria guarantee that no significant analytical gap can pass the self-evaluation loop. More criteria would create redundancy. Fewer would leave gaps.

**2026-05-06 | sanitize_for_json implemented as recursive function returning a NEW object — explicit reassignment is mandatory**
The analyzer.py output dict contains pandas/numpy float values that may be NaN or Inf (correlation matrices in particular generate NaN on diagonals and on column-pairs with insufficient data). A json default= handler does not help because the JSON encoder does not invoke default= for NaN/Inf — it emits them as the non-standard literals "NaN" / "Infinity" which Postgres JSONB rejects. The correct approach is to walk the structure recursively and replace NaN/Inf with None and tuples with lists before json.dumps. The function returns a new sanitized object — it does NOT mutate in place — so the caller MUST reassign: `analysis_response = sanitize_for_json(analysis_response)`. Forgetting the reassignment silently writes the original unsanitized dict to Supabase.
Alternatives considered: json.dumps(..., default=handler) (does not catch NaN/Inf), in-place mutation of the dict (couples mutation semantics to caller awareness, easier to break later), recursive function returning a new object with explicit reassignment (chosen — pure transform, hard to misuse if the reassignment idiom is followed).

**2026-05-06 | np.polyfit on time-series trend detection requires NaN dropna mask BEFORE the call, not after**
np.polyfit raises ValueError on real-world cleaned datasets when y contains any NaN — the linear-algebra solve fails. Cleaned data still contains NaNs in numeric columns where the cleaner chose to flag-and-include rather than impute. The fix is to compute `mask = ~np.isnan(y)` first, then `x = np.arange(len(df))[mask]` and `y = y[mask]`, then call np.polyfit only if `len(y) >= 2`; otherwise treat trend as "flat". Using df.dropna() before computing x would misalign x and y because np.arange would no longer match dropped rows.
Alternatives considered: scipy.stats.linregress (would add scipy to dependencies for one call), using datetime values directly as x to np.polyfit (TypeError — Timestamp is not numeric in numpy linalg), np.arange with NaN mask (chosen — pure-numpy, no extra dependency, correctly handles holes in cleaned data).

**2026-05-06 | Correlation matrix diagonal masking is required to prevent self-pairs in highest-pair detection**
Pearson correlation of a column with itself is always 1.0, which would always be the "highest pair" if the diagonal is not masked. The fix is to copy the correlation matrix values, set np.fill_diagonal(values, NaN) on the copy, and find the highest pair from the masked copy. The original matrix is preserved for the to_dict() output that is reported back to the LLM. Strong-pair detection is also done on the upper triangle only (j > i) to avoid duplicate pairs in both directions.
Alternatives considered: leave diagonal in place (highest_pair would always be a self-pair), mask diagonal in place (mutates the matrix that gets reported), copy + mask (chosen — preserves original output, prevents self-pair selection).

**2026-05-06 | numpy.polyfit + np.arange chosen over scipy.linregress and over raw datetime x-axis**
Three options were considered for time-series trend slope: scipy.stats.linregress (would force scipy as a runtime dependency for one call), np.polyfit with the original datetime values as x (TypeError — numpy linalg cannot solve with pd.Timestamp values), and np.polyfit with np.arange(len(df)) as x. The third works because integer row position is monotone in time when df is sorted by the datetime column, the slope is sign-correct, and the magnitude can be thresholded for the "flat" classification. No extra dependency, no type errors, correct on any sorted timeline.

**2026-09-18 | Excel data-row check confirms an empty nrows=1 peek with a full read before rejecting (added mid-build, pending review)**
Found during the Build D build; the evaluation round missed it. pandas 2.2.0's openpyxl reader stops after header + nrows physical rows and then drops trailing blank rows (`get_sheet_data`, pandas/io/excel/_openpyxl.py), while a full read keeps interior blank rows (`skip_blank_lines=False`, pandas/io/excel/_base.py). Any .xlsx whose second row is blank therefore peeks as 0 rows although the full read has data, including the common "title row, blank row, table" layout (peek 0 rows, full read 3). The approved snippet would have rejected those valid files with "no data rows"; `test_accepts_xlsx_with_blank_second_row` failed against it before this fix. Fix, Excel branch only: if the nrows=1 peek is empty, re-read the first sheet in full (the same `pd.read_excel` call as profiler.load_dataframe) and reject only if that is empty too. CSV needs no fallback, because `read_csv` skips blank lines before counting nrows (checked: a blank line under the header, 3 blank lines, a whitespace-only line, title/blank/header). Cost: workbooks with data in row 2 never reach the fallback, and header-only and empty workbooks are small. A valid workbook with a blank second row pays one full read during upload (7.4 s measured for the 7 MB test workbook), in the worker thread, and the Profiler reads it again later.
Alternatives considered: the approved nrows=1 peek alone (rejected: false rejections of valid files); a larger bounded peek such as nrows=100 (rejected: still wrong once the blank run is longer than the window); walking rows directly with openpyxl (rejected: re-implements pandas' header handling and could disagree with what the Profiler reads); confirming with the Profiler's own full read only when the fast peek is empty (chosen).

**2026-09-19 | classify_columns excludes a numeric column only when "id" is a standalone name component, via a private `_is_id_column` helper in analyzer.py (Build B, Phase 1)**
Fixes errors.md 2026-05-15. `classify_columns` (analyzer.py) dropped every numeric column whose name contained "id" anywhere (`"id" not in c.lower()`), silently removing width, valid, paid_amount, humidity, covid_19_cases and similar columns from descriptive stats, correlations, distributions, the time-series check, and the histogram, box-plot and scatter charts. Algorithm: (1) insert `_` wherever a capital letter follows a lowercase letter or digit (the camelCase boundary), (2) split on every run of characters outside `[a-zA-Z0-9]`, (3) exclude the column if any token, lowercased, equals "id". It was traced against the full test matrix. It excludes id, ID, Id, customer_id, customer-id, "customer id", id_customer, CustomerId, CustomerID, Customer_Id and grid_id; grid_id matches because of its separate "id" token, and "grid" alone does not match. It keeps width, valid, paid_amount, dividend, residual, humidity, rapid_response_time, sepal_width, petal_width, avoid, rigid and arid. No other test fixture changes: messy_data.csv's customer_id is excluded under both rules, and time_series_data.csv has no affected names. The rest of the Analyzer handles any number of numeric columns, so no other code changed. Context7 was not needed: `re` is Python's standard library, not a versioned third-party library, and its behavior was checked directly on the project's Python 3.11. Column names are always strings here, because the Analyzer reads the Cleaner's parquet and pyarrow turns non-string column names into strings on the round trip.
Known, accepted limitations (not solved; each is locked in by test_is_id_column_known_limitations so a future change is a deliberate decision):
1. An ID acronym immediately followed by another capitalized word, anywhere in the name — "IDCustomer", "IDNumber", "CustomerIDNumber" (which splits into "Customer" and "IDNumber"). There is no lowercase-to-uppercase boundary between "ID" and the next word; catching these would need acronym detection. The original evaluation described this only as a leading prefix; Code Review found the mid-name case (CustomerIDNumber), and the scope was corrected before commit.
2. "uuid" / "guid". The old substring rule excluded these only as a side effect. Real UUID/GUID data loads as object dtype, never numeric: checked for dashed text, dashless hex, a UUID stored as a 128-bit integer, and a 32-digit all-numeric value. The filter only sees numeric-dtype columns, so the real-world impact is expected to be near zero.
3. Trailing digit or plural — "id1", "id2", "related_ids". Rare in practice.
4. Separator-less concatenation — "userid", "customerid", "USERID". These are common in SQL exports and were excluded by the old rule, so this is a small true-positive regression. No token-based rule can catch them without breaking the must-keep matrix: "userid" and "valid" have the same shape (word + "id"), so an ends-with-"id" rule would also drop valid, rapid, arid, avoid, rigid and grid. Telling them apart would need a vocabulary, which is a different algorithm and out of scope.

The Profiler LLM lists them in `semantically_categorical_columns` (profiler_system.md:263) and the Cleaner LLM converts them in its Step 5 (cleaner_system.md:285-297). The prescribed Step 5 wording was checked to reach execute_cleaning_operations' DTYPE CONVERT branch, and the resulting object dtype survives parquet. That path depends on the LLMs, and a paraphrased action containing "mean" (for example "meaningless") is caught by the mean-fill branch first, so the backstop still matters when the Cleaner misses. The false-positive bug, by contrast, fired on every run with such names, so most of this fix's effect is recovering wrongly dropped columns.
Helper-function decision (Sequential Thinking), and why Build A's inline reasoning does not transfer: Build A went inline because it had five duplicated simple sites, each with its own test, plus a documented idiom at profiler.py:119 to match, and a helper name would have suggested three unchanged fill sites were missed. None of that applies here. There is one call site, so no duplication to remove. The logic is three steps with two regular expressions, which would be unreadable inline and testable only indirectly through a DataFrame per case. As a name-in, bool-out function it is tested directly against every row of the matrix, and its docstring holds the contract and the four limitations. It is module-private (leading underscore) in analyzer.py and not shared, because profiler.py and cleaner.py do not filter columns by name.

(2) build_cleaner_message fails identically and independently — same json.dumps mechanism, separate call site. Fixing only the Profiler would have moved the same crash one node downstream, after the Profiler's LLM call had been billed.
(3) Integer headers do NOT crash — json.dumps accepts int keys — and instead fail silently and more expensively. json.dumps emits them as the JSON strings "2021"/"2022", so the Cleaner's LLM names its decisions with strings, while the DataFrame's labels are still ints. execute_cleaning_operations (cleaner.py:340) then hits `col not in df.columns` for every decision, logs "Skipped decision — column '2021' not found in dataframe", and applies none of them. Verified end to end: a column with a NaN and a "fill missing with mean" decision comes out of the Cleaner with the NaN intact, after a billed LLM call, with a cleaning_report that claims the decision was made. apply_computed_column_stats is not affected — it already coerces with `str(name)` on both sides (profiler.py:198-199).
(4) The three agents must agree on what a column is called. The Profiler and the Cleaner each load the original upload themselves; the Analyzer and the Explainer read the Cleaner's parquet. pyarrow stringifies a non-string column label on the way out, and it does so with `str()`.
Decision: normalize in both loaders, at the single point where each one returns, with `df.columns = df.columns.map(str)`. Both loaders were restructured to assign into `df` across the if/elif branches and return once at the end, because each branch previously returned directly and there was no single place to put the line.
Why `map(str)` and not `astype(str)`: on a DatetimeIndex — which is exactly what a sheet whose headers are all dates produces — `astype(str)` yields "2024-01-01" while `str()` yields "2024-01-01 00:00:00". parquet produces the latter. Using astype(str) would mean the Profiler and Cleaner called a column "2024-01-01" while the Analyzer called the same column "2024-01-01 00:00:00", silently breaking every cross-agent reference (Memory MCP context, the Explainer's citations, chart labels). map(str) applies str() element-wise and matches parquet exactly. Both were measured on pandas 2.2.0 / pyarrow 23.0.1, the pinned versions. This is the reason the fix belongs at load time rather than inside the message builders: the builders could have been made defensive individually, but only normalizing the frame itself keeps the names the agents *use* consistent, and it fixes (3), which is not a serialization problem at all.
Correction to this evaluation's own headline finding, and confirmation of the Build B claim: the evaluation that preceded this build reported that uniform numeric or date headers crash the Analyzer in `_is_id_column`, and planned to record that decisions.md 2026-09-19 (Build B) was wrong to state "pyarrow turns non-string column names into strings on the round trip". Measured directly this session, that Build B claim is CORRECT and the crash finding is NOT reproducible. `df.to_parquet(path, index=False)` followed by `pd.read_parquet` returns string column labels for every index dtype tested — int64 Index, object Index of ints, RangeIndex, DatetimeIndex, and mixed str/datetime — and the Analyzer's only data source is `load_cleaned_dataframe`, which reads that parquet (analyzer.py:73-81; there is no fallback path to the original upload). `_is_id_column` does raise TypeError on a raw int or datetime label, so the hazard is real in the abstract, but nothing in the pipeline can deliver such a label to it. No correction to the Build B entry is therefore warranted, and none was written.
Accepted limitation: stringification can collide. A header row holding a numeric `2021` cell and a text `2021` cell produces two columns both named "2021", and nothing detects or disambiguates that. What the fix changes is where such a file fails, and that was traced rather than assumed. Before the fix it failed at the Analyzer: build_profiler_message silently dropped one of the two columns from column_info and the Profiler completed, the Cleaner completed, `df_cleaned.to_parquet` wrote the file successfully, and `pd.read_parquet` then raised ArrowInvalid ("Multiple matches for FieldRef.Name(2021)") — SYSTEM_ERROR two nodes downstream, after both the Profiler's and the Cleaner's LLM calls had been billed, on a profile that was already missing a column. After the fix it fails at the Profiler: duplicate labels make `df[columns]` expand the selection so `df_subset[col]` returns a DataFrame and `sampled.tolist()` raises AttributeError, before any LLM call is made, at zero API cost. The file was never analyzable either way, so failing loudly, two nodes earlier and for free is an improvement, not a regression — and it is why the collision is accepted here rather than handled. A real fix means a de-duplication policy (suffixing, or rejecting the upload with a USER_ERROR naming the duplicated header) that should be decided against real user files, not invented here. Also unchanged: date-derived names are verbose ("2024-01-01 00:00:00"), which is how they already appeared downstream.

The loader tests stage real .xlsx/.csv files in backend/uploads — the hardcoded directory both loaders read — through a fixture that deletes them afterwards. Full suite 192 passed / 16 skipped. All 5 deliberate breaks were caught: removing the stringify line from profiler.py (5 failures), removing it from cleaner.py (5), map(str)→astype(str) in profiler.py (4), the same in cleaner.py (4), and dropping the else-raise from the restructured control flow (1). The Analyzer test is a guard on pyarrow's stringification, not on this fix: as predicted by the correction above, removing the cleaner.py line does NOT fail it, and its docstring says so.
Alternatives considered: stringify inside build_profiler_message/build_cleaner_message only (fixes (1) and (2), leaves (3), and lets the frame and the message disagree); stringify in file_handler.validate_file at upload (it only peeks with nrows=1 and never hands the frame on); `astype(str)` (breaks cross-agent naming on all-date headers, as above); a shared helper imported by both agents (analyzer.py already imports profiler.py; adding a cleaner→profiler import for one line would deepen that coupling, and the two loaders are already near-duplicates of each other by prior decision); normalizing in the loaders with map(str) (chosen).

**2026-09-21 | Chart-title truncation may collide on two near-identical long column names — accepted, low priority**
`_short_name(name, limit=26)` (viz_tools.py) truncates any column name longer than 26 characters to 25 characters plus an ellipsis. Two columns whose names share their first 25 characters therefore render as visually identical strings in a scatter-plot title — `monthly_revenue_per_regio…` for both `monthly_revenue_per_region_2024` and `monthly_revenue_per_region_2025`. Accepted rather than fixed: it requires two columns agreeing on a 25-character prefix *and* both appearing in the same scatter pair, which is rare; the collision is cosmetic and confined to the title string; and the chart's underlying data, axis labels, and the `_safe_name`-derived filename are all built from the full untruncated names, so the plotted data, the axes, and the file identity remain correct and distinguishable regardless. The cost of a fix (disambiguating suffixes, or truncating from the middle to preserve distinguishing tails) is real complexity for a rare cosmetic case, and would be better decided against real user column names than invented now.
Alternatives considered: middle-truncation preserving both ends (`monthly_rev…region_2024`, keeps the distinguishing tail but is harder to read and still collides on long shared middles); appending a numeric disambiguator when two truncations match (needs cross-title state viz_tools does not have, since each chart is generated independently); raising the limit (only moves the threshold, and the 26-character limit was measured against the plot width); accepting the collision and documenting it (chosen).

**2026-09-21 | Interactive correlation matrix built as a native table of fixed-size button cells, not Recharts (Phase 2)**
The Analyst layer now renders `analysis_report.correlation_matrix` as an interactive matrix (`frontend/components/CorrelationMatrix.tsx`), placed at a fixed position in `AnalystPanel` above "Referenced charts". The evaluation proposed Recharts; the build was redirected to plain CSS layout for five reasons, each checked against the code before building: (1) Recharts has no heatmap chart type, including the installed 3.8.1, so a heatmap would be a hand-assembled scatter/rect workaround; (2) `Cell`, the per-datum styling hook such a workaround needs, is deprecated; (3) `ResponsiveContainer` inside this accordion panel is a circular measurement, not a timing race — Base UI sizes the panel from its content while `ResponsiveContainer` sizes itself from the panel; (4) `var()` custom properties do not reliably resolve in SVG `fill`, which conflicts with the tokens-only color rule; (5) Recharts tooltips are hover-driven and cannot be pinned open on touch, which is exactly the device class this phase is hardening. Hover (mouse/pen only — touch pointer events are ignored for hover) and keyboard focus (`:focus-visible` only, so tap-induced focus cannot keep a just-dismissed cell on screen) show a transient readout; a pinned readout persists until the same cell is tapped again or another cell is pinned.

**2026-09-21 | Read-only analysis access is public by analysis_id; session_id guards only the routes that change state or cost money**
An /analysis/{id} link now works for anyone who has it. The access control for reading is the analysis_id itself: a server-generated UUID4 (`uuid.uuid4()` in `upload_file`), carrying 122 random bits, which cannot be enumerated or guessed. No new secret was added to the URL. The boundary lives in two FastAPI dependencies in backend/main.py, named here so any future session can grep-verify it in seconds:

**2026-09-22 | Active pause question persisted as one nullable `pause_data jsonb` column on `analyses`, stored and returned as a raw dict, written by the orchestrator's pause-wait nodes and exposed only on GET /status**

It is doubly justified here: the payload is the Profiler's or Cleaner's parsed LLM JSON, stored whole (profiler.py `domain_pause_data = parsed`; cleaner.py `missing_value_pause_data` / `outlier_pause_data = parsed`), and it already differs from its written spec (3 missing-value options vs. cleaner.md's 4; errors.md 2026-09-22). A strict model would turn LLM variance into a 500 on the public, polled /status route. `StatusResponse.pause_data: dict | None`.
- **Per-type shapes (defined by the prompts, not by Python).** The contracts that fill this column:
  - Domain (profiler_system.md §8): `{type:"domain_confirmation_required", domain_hypothesis, domain_confidence_score, supporting_signals[], options:[{id:"confirm",label,action},{id:"correct",label,action}]}`.
  - Missing value (cleaner_system.md §8.1): `{type:"missing_value_decision_required", column_name, missing_pct, missing_count, total_rows, what_this_column_represents, provenance_interpretation, domain_context, options:[impute{method,assumption}, exclude_column{consequence}, exclude_rows{consequence}]}`. **One column per pause**, not bundled; multiple columns pause sequentially.
  - Outlier (cleaner_system.md §8.2/8.3): `{type:"outlier_decision_required", domain_context:"medical"|"financial", column_name, outlier_value, outlier_count, sd_distance, column_mean, column_std, clinical_significance_note|financial_context_note, options:[…]}`. The option ids are a fixed pair per domain (`include_with_annotation`/`exclude_pending_clinical_review` or `treat_as_valid`/`flag_as_suspected_error`); only labels and notes are LLM-written.
- **Write location: orchestrator.py, not the agents.** The pause status is written only in `domain_pause_wait_node` and `cleaner_pause_wait_node`, and `pause_data` must land in that same single update so the status can never show a pause without its question. Putting the write in profiler.py/cleaner.py would have meant a second update (a partial-failure window) or moving the status transition into the agents. The domain node writes `state.get("domain_pause_data")`. The cleaner node sets `pause_data` inside the same `if/elif` that picks the status, so status and payload come from one decision; its fallback branch (neither payload set, unreachable via `route_after_cleaner`) writes `pause_data=None` explicitly. The nodes have no try/except, so a failed write propagates to `run_pipeline`'s existing SYSTEM_ERROR handler — no new error path, and the known "everything is SYSTEM_ERROR" limitation (errors.md 2026-09-18) is inherited, not fixed.
- **Pre-existing inconsistency, out of scope:** orchestrator.py's module docstring says it contains "graph structure only", but its pause-wait nodes already held DB-polling logic before this build. This build adds one key to each node's existing update rather than moving that logic.
- **Clearing:** POST /resume sets `pause_data=None` in the same single update that stores `user_pause_response` and restores the status, so the invariant holds at both edges.
- **Placement: GET /status only.** It is the route polled during a pause and the one AnalysisProgress consumes; it returns `pause_data` only when the status is a pause value (a stale stored value is never returned otherwise). GET /api/analysis/{id} deliberately does not carry it — it is the results view, where `pause_data` is null by invariant — and `test_get_analysis_never_includes_pause_data` locks this in under every status. Both routes remain public (`get_public_read_access`). `pause_data` is identical for owner and visitor, because it is descriptive content; only the controls built on it (submitting a resume) need owner-gating, which is the later frontend build's job via `isOwner` (decisions.md 2026-09-21).
Alternatives considered: three per-type columns (rejected, above); a strict pydantic `PauseData` model (rejected, above); writing from profiler.py/cleaner.py (rejected: breaks single-update atomicity); also exposing `pause_data` on GET /api/analysis/{id} (rejected: duplicate field with no consumer); clearing `pause_data` in the wait node after the response arrives (rejected: a second write, and a window where status is no longer paused but the question remains).

**2026-09-22 | POST /resume validates the response against the stored pause question and writes only if that exact pause is still active (409 otherwise); per-type response contract fixed; includes a correction of this build's earlier "cannot strand" claim**
The `{"response": {...}}` envelope is unchanged and the route stays on strict `get_session`. The inner response is now:
- `domain_pause`: `{"pause_type":"domain_pause","option_id":"confirm"}` or `{"pause_type":"domain_pause","option_id":"correct","corrected_domain":"<non-empty text>"}`
- `missing_value_pause`: `{"pause_type":"missing_value_pause","column_name":"<pause_data.column_name>","option_id":"<an id in pause_data.options>"}`
- `outlier_pause`: `{"pause_type":"outlier_pause","column_name":"<pause_data.column_name>","option_id":"<an id in pause_data.options>"}`
`_validate_pause_response` (main.py) returns 400 before any write when `pause_type` differs from the current status, when `option_id` is not among the stored `pause_data.options[].id`, when `column_name` differs from the stored one (missing-value and outlier), or when `correct` has a missing or blank `corrected_domain`. Option ids are read from the stored payload, not hardcoded, so the check tolerates prompt changes such as the 3-vs-4 option drift. Echoing `pause_type` and `column_name` makes each answer self-describing, which the later consumption fix needs in order to accumulate several answers (errors.md 2026-09-22). **Escape hatch:** when there is no stored question with usable option ids to validate against — `pause_data` null (a row paused before this build, or the unreachable cleaner fallback branch), no `options` key, an empty `options` list, or options without a non-empty string `id` — `option_id` is not checked and a warning is logged, but `pause_type` is, and so is `column_name` for missing-value and outlier pauses whenever the stored `column_name` is a non-empty string. **What each protection covers:** the **`column_name` check** is what rejects an answer from a stale tab, written for a pause that is no longer the active one — but only when a usable `column_name` is stored and the active pause is on a different column. A stale answer is still accepted when the Cleaner re-pauses on the same column (the question is effectively the same, so the harm is small) or when no `pause_data` is stored (the unreachable cleaner fallback branch, or a row paused before this build). The **conditional write** covers only the pause changing between this request's own read and its write: the update matches `id`, the validated `status`, and the `updated_at` read alongside it (`.is_("updated_at", "null")` if that was null), which the pause-wait node stamps in the same write that sets each pause. If it matches no rows, the endpoint returns **409** without writing. The client does not send which pause it is answering, so the 409 by itself cannot catch a stale tab. Before this build the endpoint accepted any dict. The frontend's `resumeAnalysis` (lib/api.ts) has no callers, so nothing in the running app changes; `test_resume_valid_domain_pause` was updated from the old free-form `{"decision":"confirm"}` to this contract.
**Correction — an earlier claim in this build was wrong.** The second evaluation pass for this build stated that the escape hatch (then: null `pause_data` only) meant "strict validation can never strand a row". That was false. The report-only Code Review run after the first implementation found a real stranding case: if the LLM's stored question had no `options` key, an empty `options` list, or options without ids, the allowed-id list came out empty (or `[None]`), every legitimate answer got a 400, and — because the pause-wait node polls with no timeout — the analysis would have been stuck in the pause for good. Fixed in this same build by widening the escape hatch to all of those shapes (tests cover the null, no-options-key, empty-list and options-without-ids cases separately). The same review found two further bugs, also fixed in this build and not pre-existing: (a) `response["option_id"]` could raise KeyError (a 500) when a stored option lacked an `id`, because `None` then passed the membership check — now `response.get(...)`, and unusable ids are filtered out; (b) the resume update matched only on `id`, so a delayed resume validated against one pause could land after the Cleaner had re-paused on another column and answer the wrong question. The fix as first specified, `.eq("status", status)`, would not have caught that exact scenario, because a Cleaner re-pause on another column repeats `missing_value_pause`. That is why the write is also conditional on `updated_at` (above). A final scoped Code Review of those fixes then found that the widened escape hatch also skipped the `column_name` check, so an answer from a stale tab for another column would be accepted whenever option ids were unusable — and that the 409 had been described as covering that case, which it cannot. Fixed in this build too: the escape hatch skips only `option_id`, and the wording above now states exactly what each protection covers. Details in errors.md 2026-09-22.
Known limitation (explicitly out of scope): the pipeline does not yet *use* these answers correctly — the Profiler ignores a domain answer, and pauses on more than one column likely loop (errors.md 2026-09-22). This contract is the interface the consumption fix and the frontend pause UI will build against.
Alternatives considered: keep accepting any dict (rejected: the frontend would have no defined contract, and garbage would be silently stored); hardcode the option enums (rejected: the options are LLM-emitted and already drift from spec); reject when stored pause_data is null or has no usable option ids (rejected: would strand such a row with no recovery path); an unconditional write (rejected after Code Review: lets a stale resume answer a newer pause); a status-only conditional write (rejected: a Cleaner re-pause repeats the same status value); a conditional match on the stored `pause_data` itself (rejected: jsonb equality through PostgREST filters is awkward, and `updated_at` is already stamped atomically with each pause — an exact-match filter on it was verified read-only against the live table).
